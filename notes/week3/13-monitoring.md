## CloudTrail 組織証跡
- **組織証跡**: 管理アカウント（または**委任管理者**）が作成。**管理アカウントと全メンバーアカウントのイベント**を記録。既存の管理アカウントの証跡を組織証跡に変更することもできる
- **コンソールで作ると必ずマルチリージョン**。単一リージョン証跡は CLI のみ。**パーティション（GovCloud 等）をまたぐ場合は各パーティションで作成**
- 作成すると各メンバーアカウントに**同名の証跡のコピー**ができる。**メンバーアカウントは見られるが、削除・ログ停止・記録内容の変更はできない**
- サービスにリンクされたロール **`AWSServiceRoleForCloudTrail`** が作られる。**アカウントが組織に加わると自動で記録開始、抜けると証跡は削除**（それまでのログは S3 に残る）
- **オプトインリージョン**: マルチリージョン証跡のホームリージョンがオプトインリージョンの場合、メンバーアカウントがそのリージョンを有効化していないとログが送られない
- S3 バケット構成: **組織 ID のフォルダ → アカウント ID のサブフォルダ**。既定でバケットにアクセスできるのは**管理アカウントのみ**
- **イベント履歴（Event history）は 90 日分の管理イベントで、サインイン中のアカウントのものだけ**（管理アカウントからメンバーの分は見えない）。長期保存・組織横断は証跡（S3）か CloudTrail Lake
- 証跡の検証エラー（S3 バケットポリシー不備、KMS 権限不足など）があっても**メンバーアカウントに証跡は作られる**（`get-trail-status` で確認）
- データイベントのリソース指定は、コンソールには管理アカウントのものしか出ないが、**メンバーアカウントのリソースの ARN を追加でき、クロスアカウントのアクセス設定は不要**

### イベントの種類
| 種類 | 内容 | 既定 |
|---|---|---|
| **管理イベント** | コントロールプレーン操作（リソース作成、セキュリティ設定、ConsoleLogin など） | **記録される** |
| **データイベント** | データプレーン（S3 オブジェクトの GetObject/PutObject、Lambda Invoke など。大量） | **記録されない** |
| **ネットワークアクティビティイベント** | 原文に 4 種類目として記載（詳細は未確認） | 記録されない |
| **Insights イベント** | 通常パターンから外れた API 呼び出し数／エラー率 | **記録されない**（追加料金） |

- **Insights**: 過去の管理・データイベントから**ベースライン**を作り、逸脱したときに生成。**API 呼び出し率は書き込み（write）の管理イベントが対象**。エラー率は読み書きどちらでも可。**Insights は、その証跡（データストア）が対応するイベントを記録していることが前提**。Insights イベントは元のイベントと**同じリージョン**に生成。**データイベントの Insights は証跡のみで、イベントデータストアは非対応**

### ログファイル整合性検証
- ログごとに**ハッシュ（SHA-256）**を作り、**1 時間ごとにダイジェストファイル**（直近 1 時間のログのハッシュ一覧）を作成して **SHA-256 with RSA で署名**。リージョンごとに別のキーペア。**変更・削除・偽造を検知できる**（「その期間にログが配信されなかった」ことの証明にも使える）
- ダイジェストは**同じ S3 バケットの別フォルダ**に配信（ログと分けることで粒度の細かいポリシーが可能）。前のダイジェストの署名も含むので**チェーン**になる
- **有効化しただけでは検証されない**（検証は AWS CLI か自作）。検証は CloudTrail が配信した場所のファイルが対象で、移動したログは自作の検証が必要
- ダイジェストの保護には **S3 MFA Delete** が挙げられている

### CloudTrail Lake（注意）
- SQL でイベントを保存・クエリする機能。**組織イベントデータストア**は管理アカウントか委任管理者が作成（**実体は管理アカウントに存在**）。メンバーアカウントは**見えない・変更できない・既定ではクエリもできない**
- **Insights の有効化、証跡イベントのコピー、ダッシュボードは管理アカウントのみ**（委任管理者は不可）
- **原文の注記: 2026-05-31 以降、CloudTrail Lake は新規顧客の受付を終了**（既存顧客は継続利用可）。試験範囲の記述としては古い可能性があるので、出題されても「証跡 + S3 + Athena」の方が無難

## AWS Config
### アグリゲーター（データ集約）
- **アグリゲーター**: **複数アカウント・複数リージョン**（または組織全体）の構成・コンプライアンスデータを**集約アカウント**で閲覧する Config のリソース
- **読み取り専用**。**アグリゲーター経由でルールの展開や送信元アカウントの変更はできない**。追加料金なし
- ソースアカウントは個別指定、または **Organizations 経由**で取得。**Organizations のアカウントを集約する場合は認可（Authorization）が不要**。組織外のアカウントは**ソース側が集約アカウントを認可**する必要がある
- 用途: コンプライアンス監視、変更追跡、リソース関係の分析

### 組織ルール・組織適合パック（展開）
- 管理アカウントから、**全アカウントに Config ルール（または適合パック）を一括で作成・更新・削除**。**除外アカウントも指定可能**。メンバーアカウントからは**変更できない**ため、ガバナンスの強制になる
- **組織ルールは API/CLI のみ**（コンソール非対応）。適合パックの組織展開のコンソール操作は **Systems Manager** 経由
- **API 呼び出しはリージョン単位**。他リージョンに展開するにはリージョンを切り替えて呼ぶ
- **新規アカウントが組織に加わるとルール／適合パックが展開され、抜けると削除される**。ただし**レコーダーがない場合の再試行は 7 時間**まで（その間にレコーダーを作る必要がある）
- **展開前に Config の記録（recorder）をオンにしておく**
- **委任管理者を使う場合、管理アカウント側のサービスリンクロール（SLR）は自動作成されない**。IAM で手動作成しないと、委任管理者から**管理アカウントには展開できない**（メンバーアカウントには展開できる）
- 管理アカウントと委任管理者で展開したものは**互いに見えない**（Describe 系 API は呼び出したアカウントから展開したものだけ）
- **適合パック**: Config ルールと修復アクションを YAML テンプレートにまとめた単位。**アカウント＋リージョン、または組織**にまとめてデプロイ。サンプルテンプレートあり

### 修復（Remediation）
- **SSM Automation ドキュメント**で修復。AWS 提供のドキュメントか自作。**手動 or 自動**を選べる
- 自動修復で**失敗したときの再試行回数・秒数を設定可**（再試行の実行にも SSM Automation の料金がかかる）
- **管理できるのはサービスリンクルール以外**のルール
- **注意**: 自動修復は**定期的に取得されるコンプライアンススナップショット**に基づくため、**準拠済みのリソースに対して修復が始まることがある**（古い評価結果による）

## CloudWatch: クロスアカウントオブザーバビリティ（OAM）
- **監視アカウント**（データを見る側）と**ソースアカウント**（データを出す側）。共有できるのは**メトリクス、ロググループ、X-Ray トレース、Application Signals、Application Insights、Internet Monitor**。メトリクスは名前空間、ログはロググループで**絞り込み可**
- **Sink（シンク）** = 監視アカウント側の接続点（**アカウントあたり 1 リージョンに 1 つ**、監視アカウントが管理）。**Link（リンク）** = ソース側が作る接続（**ソースアカウントが管理**）。リンクの削除もソース側から
- **リージョン内**の話（クロスアカウント。リージョンをまたぐ表示は別機能のダッシュボード）
- **Organizations で組織／OU 単位にリンクすると、新規アカウントが自動でオンボードされる**（推奨）。CloudFormation テンプレートで組織／OU 内の全アカウントをソースにできる（テンプレートの詳細は未確認）
- 上限: 監視アカウント 1 つにつき**最大 100,000 のソースアカウント**、ソースアカウント 1 つは**最大 5 つの監視アカウント**にデータ共有
- 監視アカウント兼ソースアカウントにした場合、**自分のデータだけを送り、自分のソースアカウントのデータは中継しない**
- テレメトリ種別の不一致: **監視アカウントの選択が多い → リンク成立し、両方で選んだ種別のみ共有**。**ソース側の選択が多い → リンク作成は失敗し、何も共有されない**
- **リンク後に新しくデータポイントが出るまで**、監視アカウントのコンソールにメトリクス名が出ない
- **シンクを削除するには先にすべてのリンクを削除**。**新しい専用アカウントを監視アカウントにするのが推奨**。**ログ・メトリクス・Application Signals は追加料金なし、トレースは最初のコピーが無料**

## CloudWatch Logs: 集約の方法
| 方法 | 特徴 |
|---|---|
| **クロスアカウントオブザーバビリティ** | 監視アカウントから、リンクされたソースアカウントのロググループを検索・可視化（原文は「シームレスに検索・可視化・分析」。Logs Insights での利用やコピーの有無の詳細は未確認） |
| **サブスクリプションフィルター（クロスアカウント）** | ログイベントを**リアルタイムに** Kinesis Data Streams / Firehose に送り、独自処理（例: セキュリティ部門の侵入検知）。**ロググループと宛先（destination）は同じリージョン**が必須（宛先が指すリソースは別リージョンでもよい） |
| **データ集約（centralization ルール）** | Organizations と連携し、**ルールで複数アカウント・リージョンのログを 1 つの宛先アカウントにレプリケート**。バックアップリージョンを設定可能 |

- 集約ログには **`@aws.account` / `@aws.region` / `@source.log`** のシステムフィールドがあり、送信元で絞り込める
- **集約は「ルール作成後に届いた新しいログ」のみ**。過去ログは集約されない
- 宛先アカウントで**カスタマー管理 KMS キー**を使う場合、キーに**タグ `LogsManaged = true`** が必要

## CloudWatch アラーム
- **複合アラーム**: 他のアラームの状態を `ALARM("x") OR/AND/NOT ...` の**ルール式**で組み合わせる。関数は ALARM / OK / INSUFFICIENT_DATA。**通知の重複・ノイズを減らす**用途。アクションは SNS、Lambda、Systems Manager（OpsItem / Incident Manager）、調査（investigation）
- **複合アラーム同士の循環依存**を作ると**評価されなくなり、削除もできなくなる**。回避は片方の AlarmRule を `False` に変更

## X-Ray
- **サンプリングルール**: 何割のリクエストを記録するか。**既定は「毎秒最初の 1 リクエスト（reservoir）＋それ以降の 5%」**。reservoir により、リクエストがある限り毎秒最低 1 トレースを記録
- **コンソールでルールを定義し SDK にサービスから読ませる**と、(1) 複数インスタンスの reservoir が**合算されて実効サンプリング率が上がる問題**を避けられ、(2) **再デプロイなしで変更**できる。サービスが各インスタンスにクォータを割り当てる
- **サンプリングはペアレントベース**: 最初の X-Ray 対応サービス（ルート）が**1 回だけ決定**し、下流は**自身のルールに関係なくその決定に従う**。下流サービスのルールだけ厳しくしても効かない → **ルートサービスにルールを設定する**
- ルールが効くのは、サンプリング決定がまだされていない場所（API Gateway 等の入口、新しいトレースを始める非同期処理）
- 対応: API Gateway、AppSync、Step Functions（アクティブトレーシング）、EC2/ECS/Beanstalk 上の ADOT または X-Ray SDK。**ベストエフォート**でありレートは厳密に一致しない
- クロスアカウントのトレース閲覧は上記の **OAM（Traces を共有）** で行う

## 判断ポイント
- 「全アカウントの API 操作を改ざん不能に記録」→ **組織証跡 + 整合性検証**（メンバーは証跡を変更・停止できない。S3 バケットは既定で管理アカウントのみアクセス可）。ログ専用アカウントに置く構成は一般的な設計で、今回の原文では未確認
- 「ログが変更・削除されていないことを証明」→ 整合性検証（ダイジェスト）。有効化だけでは検証されない
- 「異常な API 呼び出し（急増・エラー）を検出」→ CloudTrail Insights（既定オフ、追加料金）
- 「メンバーアカウントの証跡を見られるか」→ 見えるが、変更・削除は不可
- 「全アカウントのコンプライアンスを 1 画面で」→ Config アグリゲーター（Organizations なら認可不要）。**ルールを配りたい**なら組織ルール / 適合パック（アグリゲーターでは展開できない）
- 「新規アカウントにも Config ルールを自動適用」→ 組織ルール / 適合パック。ただしレコーダーが 7 時間以内に必要
- 「非準拠リソースを自動修復」→ Config ルール + SSM Automation の自動修復
- 「複数アカウントのメトリクス・ログ・トレースを 1 つのアカウントで」→ クロスアカウントオブザーバビリティ（Organizations で自動オンボード）
- 「別アカウントのログをリアルタイム処理」→ サブスクリプションフィルター（宛先と同一リージョン）。「組織全体のログを 1 アカウントに集める」→ centralization ルール
- 「アラーム通知の氾濫を減らす」→ 複合アラーム
- 「X-Ray で下流サービスのサンプリング率を変えたい」→ ルートサービスのルールを変更（ペアレントベース）
