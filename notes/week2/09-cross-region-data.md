# Week2-9: データ層のリージョン間構成

出典（2026-09-25 に原文を curl で確認）: Aurora User Guide「Using Amazon Aurora Global Database」、DynamoDB Developer Guide「Global tables」「How DynamoDB global tables work」、S3 User Guide「Replicating objects」「What does Amazon S3 replicate?」「Requirements and considerations for replication」、RDS User Guide「Cross-Region read replicas」、ElastiCache User Guide「Replication across AWS Regions using global datastores」。DR の位置づけは 08 ノート

## 比較表
| サービス | 仕組み | 書き込み | 特徴 |
|---|---|---|---|
| Aurora Global Database | ストレージ層の専用インフラで非同期レプリケーション。遅延は通常 1 秒未満 | プライマリリージョンのみ。セカンダリからの書き込みは write forwarding で転送 | プライマリ 1 + セカンダリ最大 10 リージョン。障害時のフェイルオーバー（セカンダリの昇格）は通常数分（Aurora User Guide。「1 分未満」は DR ホワイトペーパーの記述で、User Guide では確認できず） |
| DynamoDB グローバルテーブル | 全レプリカがマルチアクティブ | どのレプリカでも読み書き可 | MREC（既定・非同期・last writer wins）と MRSC（同期・強い整合性）。SLA 99.999% |
| S3 レプリケーション（CRR/SRR） | バケット間の非同期コピー | ソースバケット | バージョニング必須。S3 RTC で 99.99% を 15 分以内（SLA つき） |
| RDS クロスリージョンリードレプリカ | エンジンのレプリケーションによる非同期 | ソースのみ | 昇格は手動。昇格後は独立した DB になる |
| ElastiCache Global Datastore | Valkey / Redis OSS のリージョン間非同期レプリケーション | プライマリクラスターのみ | セカンダリは読み取り専用。**リージョン間の自動フェイルオーバーは非対応（手動で昇格）** |

## Aurora Global Database
- プライマリ 1 リージョンに書き込み、最大 10 の読み取り専用セカンダリリージョン。レプリケーションはデータベースエンジンではなくクラスターストレージ層が担うので、プライマリへの性能影響が小さい
- **Global Database のライターエンドポイント**は、スイッチオーバーやフェイルオーバー後も常にプライマリを指す
- 切り替えは2種類（試験で区別される）:
  - **スイッチオーバー**（旧「managed planned failover」）: 計画作業（リージョンのローテーションなど）用。健全な状態で、**データ損失なし**でプライマリを移す
  - **フェイルオーバー**: プライマリリージョンの障害からの復旧用（クロスリージョンフェイルオーバー）
- **write forwarding**: セカンダリクラスターで受けた書き込みをプライマリに転送する。アプリは最寄りのセカンダリに接続したまま書き込める（書き込み自体はプライマリで実行）
- セカンダリは読み取り専用なので、最大 16 個のリーダーインスタンス（通常のクラスターは 15）を持てる
- 制約: Backtrack 非対応、セカンダリの Aurora Auto Scaling 非対応、Secrets Manager 統合は Global Database 非対応、マネージドのスイッチオーバー/フェイルオーバーはプライマリとセカンダリで**エンジンのメジャー/マイナーバージョンが同じ**であることが必要
- 08 ノートの DR ホワイトペーパーは「最大5つのセカンダリリージョン」と書いているが、Aurora User Guide の現行の記述は**最大 10**。**Aurora User Guide を優先**（ホワイトペーパーの記述が古い可能性）

## DynamoDB グローバルテーブル
- 全レプリカで同じテーブル名・主キー。どのレプリカでも読み書きでき、他のレプリカへ自動でレプリケートされる。既存の DynamoDB API をそのまま使う（アプリ変更不要）
- **MREC（既定）**: 非同期。通常 1 秒程度以内にレプリケート。同一アイテムの同時更新は**内部タイムスタンプが最新のものが勝つ（last writer wins）**。強い整合性のある読み取りは、書き込みを受けたリージョンでのみ最新を保証する
- **MRSC**: 同期レプリケーション。**どのレプリカでも強い整合性のある読み取りが最新を返す**。**RPO ゼロ**が必要な場合の選択肢
  - **ちょうど 3 リージョン**が必要（3 レプリカ、または 2 レプリカ + witness 1 つ。witness は読み書き不可）
  - 対応リージョンは限られる。作成時に**空のテーブル**である必要がある。同一アカウント構成のみ
  - **整合性モードは作成後に変更できず**、1 つのグローバルテーブルで混在もできない
- MREC のレプリカ数はリージョン数まで。既存テーブルにレプリカを追加して作る
- アカウント構成: 同一アカウント（1 つの IAM/KMS 境界）と**マルチアカウント**（レプリカを別アカウントに置き、アカウントごとに IAM/KMS/課金/CloudTrail を分離）。マルチアカウントは MRSC 非対応
- 「マルチリージョンで、ローカル書き込み、低遅延、競合は許容」→ グローバルテーブル（MREC）

## S3 レプリケーション
- **CRR**（リージョン間）と **SRR**（同一リージョン）。SRR の用途: ログ集約、本番/テストのコピー、データ主権など
- 要件: ソース・宛先の**両バケットでバージョニング有効**、S3 が引き受ける IAM ロール、必要なリージョンが有効化されていること
- **レプリケーションは設定後の新しいオブジェクトが対象**。既存オブジェクトは **S3 Batch Replication** でオンデマンドにコピーする（S3 RTC は Batch Replication には適用されない）
- **S3 RTC（Replication Time Control）**: 新規オブジェクトの 99.99% を 15 分以内にレプリケート（SLA つき）。監視用メトリクスも出る
- **双方向（two-way）レプリケーション**: 2 つのバケットを相互にレプリケーションする。**レプリカ変更の同期（replica modification sync）**を有効にして、レプリカ側のメタデータ変更も同期する。**Multi-Region Access Point** と組み合わせて使える
- **レプリケーションされないもの・注意**:
  - **削除マーカーは既定ではレプリケートされない**（非タグベースのルールで有効にできる。**ライフサイクルによる削除のマーカーは複製されない**）。08 ノートの「DR 側を悪意ある削除から守る」根拠
  - **すでにレプリケートされたオブジェクトは再レプリケートされない**（A→B→C の連鎖はしない）。連鎖させたいときは Batch Replication
  - Glacier Flexible Retrieval / Deep Archive、Intelligent-Tiering のアーカイブアクセス層のオブジェクトは対象外
  - **ライフサイクルの動作**（有効期限切れなど）は複製されない。両バケットに同じライフサイクル設定を入れる
  - 暗号化オブジェクトは SSE-S3 / SSE-KMS / DSSE-KMS / SSE-C とも対応（KMS の扱いは 10 ノートで整理する）
- クロスアカウントレプリケーションもできる。既定では、別アカウントへのレプリケーションでは削除マーカーが複製されない

## RDS クロスリージョンリードレプリカ（Aurora 以外）
- 非同期レプリケーション。障害時は**手動で昇格**させる。昇格すると独立した DB になり、レプリケーションは切れる。昇格には数分かかり、再起動を伴う（08 ノート）
- **暗号化されたレプリカを別リージョンに作るには、ソースが暗号化されている必要があり、宛先リージョンの KMS キーを指定する**
- 用途: DR、読み取りの分散、リージョン間の DB 移行
- クロスリージョンレプリケーションにはデータ転送料金がかかる
- Aurora との違い: RDS リードレプリカはリージョン障害時の昇格が数分で遅延も大きくなりうる。Aurora Global Database の方が RTO/RPO が小さい（08 ノート）

## ElastiCache Global Datastore（Valkey / Redis OSS）
- プライマリ（読み書き）+ セカンダリ（読み取り専用、別リージョン）。非同期レプリケーション。**ノードベースのクラスターのみ**（サーバーレス非対応）
- 用途: 低レイテンシーの地理的に近い読み取り、DR（セカンダリを手動でプライマリに昇格）
- **リージョン間の自動フェイルオーバーには対応しない**。設計時は、アプリ側またはランブックで昇格手順を自動化する

## 判断ポイント
- 「RDB のリージョン間 DR で、RTO が分単位・遅延 1 秒未満」→ Aurora Global Database
- 「計画的なリージョン移行で、データ損失なし」→ Aurora のスイッチオーバー
- 「リージョン障害からの復旧」→ Aurora のフェイルオーバー
- 「セカンダリリージョンのアプリから書き込みたい（書き込みはプライマリで実行）」→ Aurora write forwarding
- 「マルチリージョンで、全リージョンで書き込み、競合は last writer wins で許容」→ DynamoDB グローバルテーブル（MREC）
- 「マルチリージョンで **RPO ゼロ**、強い整合性のある読み取り」→ DynamoDB グローバルテーブル MRSC（3 リージョン）
- 「別アカウントごとにガバナンスを分離したグローバルテーブル」→ マルチアカウントグローバルテーブル
- 「S3 を 15 分以内でリージョン間コピー（SLA 必要）」→ CRR + S3 RTC
- 「すでにあるオブジェクトもコピーしたい」→ S3 Batch Replication
- 「2 リージョンの S3 に相互で書き込む」→ 双方向レプリケーション + replica modification sync（+ Multi-Region Access Point）
- 「Redis のリージョン間レプリケーション」→ ElastiCache Global Datastore（自動フェイルオーバーなし）
- 「暗号化した RDS のクロスリージョンレプリカ」→ ソースが暗号化済み + 宛先リージョンの KMS キーを指定

## Q&A（答えを隠して考えてから確認）
### Q1. RDB のリージョン間 DR で、障害時のセカンダリ昇格を数分以内、レプリケーション遅延を 1 秒未満にしたい。どうする？
<details><summary>答え</summary>
Aurora Global Database。ストレージ層で非同期レプリケーションする（Aurora User Guide では RTO は分単位、RPO は通常秒単位、フェイルオーバーで新プライマリは通常数分で昇格）。RDS（Aurora 以外）のクロスリージョンリードレプリカは昇格に数分かかり再起動も伴う。
</details>

### Q2. Aurora Global Database で、計画的なリージョンローテーションをデータ損失なしで行いたい。どの操作？
<details><summary>答え</summary>
スイッチオーバー（旧 managed planned failover）。健全な状態でデータ損失なしにプライマリを移す。リージョン障害からの復旧はフェイルオーバー。
</details>

### Q3. マルチリージョンで RPO ゼロ、どのレプリカでも強い整合性のある読み取りをしたい。どうする？
<details><summary>答え</summary>
DynamoDB グローバルテーブルの MRSC。同期レプリケーションで、ちょうど 3 リージョン（2 レプリカ + witness も可）が必要。整合性モードは作成後に変更できず混在も不可。既定の MREC は非同期で last writer wins。
</details>

### Q4. S3 のリージョン間コピーを SLA つきで 15 分以内にしたい。すでにあるオブジェクトもコピーしたい。どうする？
<details><summary>答え</summary>
CRR + S3 RTC（99.99% を 15 分以内）。既存オブジェクトは S3 Batch Replication でコピーする。ただし S3 RTC は Batch Replication には適用されない。
</details>

### Q5. 暗号化した RDS のクロスリージョンリードレプリカを作りたい。条件は？
<details><summary>答え</summary>
ソースが暗号化されていることと、宛先リージョンの KMS キーを指定すること。
</details>

### Q6. ElastiCache Global Datastore でリージョン障害が起きた。自動でフェイルオーバーされる？
<details><summary>答え</summary>
されない。リージョン間の自動フェイルオーバーは非対応で、セカンダリを手動でプライマリに昇格する。アプリ側やランブックで手順を自動化する。
</details>
