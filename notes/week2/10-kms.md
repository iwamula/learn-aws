## マルチリージョンキー
- 別リージョンの KMS キーを**同じキーとして交換可能に使える**仕組み。関連キーは**同じキー ID とキーマテリアル**を持つ。あるリージョンで暗号化し、別リージョンで**再暗号化も KMS のクロスリージョン呼び出しもなしに**復号できる
- 1 セットにプライマリキーがちょうど 1 つ。レプリカは他リージョン（**同じパーティション内**）に作る。1 リージョンにつきセット内のキーは 1 つ。**プライマリリージョンの切り替え**もできる
- **既存のシングルリージョンキーをマルチリージョンに変換できない**（逆も不可）。作成時に決まる。既存データを使うには新しいマルチリージョンキーで**再暗号化**が必要
- **共有プロパティ**（プライマリから同期）: キー ID、キーマテリアル、マテリアルの起点、キー仕様、キー用途、自動ローテーション。**独立プロパティ**（同期されない）: **キーポリシー、グラント、有効/無効、エイリアス、タグ、説明**。レプリカごとに管理する
- 自動ローテーションの有効化/無効化とオンデマンドローテーションは**プライマリのみ**。AWS_KMS 起点ならマテリアルの全バージョンがレプリカに配られる。**EXTERNAL 起点（インポート）はレプリカごとに同じマテリアルを自分でインポート**する
- **プライマリの削除は、全レプリカが削除されるまで実行されない**
- **カスタムキーストアにはマルチリージョンキーを作れない**。**AWS マネージドキーは常にシングルリージョン**
- 対応キー: 対称暗号化、非対称、HMAC、インポートマテリアル付き
- 課金・クォータ: セット内の**各キーが 1 キーとして**数える。クォータはリージョンごと
- 用途: DR、グローバルデータ管理、分散署名、Active-Active。**クライアント側暗号化（AWS Encryption SDK など）で最も効く**
- **多くの AWS サービスはマルチリージョンキーをシングルリージョンキー扱いにする**。例: **S3 CRR は、両リージョンが関連するマルチリージョンキーでも、宛先リージョンのキーでデータキーを復号・再暗号化する**。マルチリージョンキーにしても S3 の CRR 構成は変わらない（サービスごとの記述を確認する）

## キーポリシーとクロスアカウント
- **KMS のキーポリシーは他のリソースポリシーと違い、アカウントに自動でアクセスを与えない**。既定のキーポリシーの `Principal: arn:aws:iam::<アカウント>:root` / `kms:*` の文が、**「IAM ポリシーでアクセスを委任できる」ようにする**文。これがないと、キーを許可する IAM ポリシーは効かない（**拒否する** IAM ポリシーは効く）。キーが管理不能になるリスクも下げる
- API/CLI で作成して既定ポリシーを指定しないと、上の 1 文だけの既定ポリシーになる。コンソールで作ると管理者・利用者・AWS サービス利用の文が追加される
- **クロスアカウントは 2 つの許可が両方必要**（どちらか片方では不十分）:
  1. **キー所有アカウントのキーポリシー**が外部アカウント（または外部のユーザー/ロール）を許可
  2. **外部アカウントの IAM ポリシー**が自アカウントのユーザー/ロールに委任
- キーポリシーの Principal を外部アカウント root にすると、外部アカウントの IAM 管理者が委任先を決められる。特定ロールを指定すると、外部側の IAM ポリシーがあっても**キーポリシーで指定した範囲**に制限される
- **クロスアカウントで有効な操作は限られる**: 暗号操作、CreateGrant、DescribeKey、GetKeyRotationStatus、GetPublicKey、ListGrants、RetireGrant、RevokeGrant。ScheduleKeyDeletion などを許可しても**効かない**
- 外部アカウントの権限は、**そのアカウントがキーのあるリージョンで有効**（オプトインリージョン）な場合のみ有効
- クロスアカウントの操作は**呼び出し側とキー所有側の両方の CloudTrail** に記録される

## リージョン間コピー時の暗号化（サービス別）
| 対象 | 暗号化の扱い |
|---|---|
| S3 CRR | SSE-S3/SSE-KMS/DSSE-KMS のオブジェクトは、宛先でも**同じ種類の暗号化**（宛先バケットの既定暗号化は使わない）。**SSE-KMS/DSSE-KMS は既定ではレプリケートされない**。`SourceSelectionCriteria`（SseKmsEncryptedObjects を Enabled）で明示的に有効化し、宛先の**対称 KMS カスタマーマネージドキー ID** を指定する。レプリケーション用 IAM ロールにソースキーの `kms:Decrypt` と宛先キーの `kms:Encrypt`（Bucket Key 利用時は `kms:GenerateDataKey` も）が必要。**KMS キーが別アカウントなら、キー所有者がロールのアカウントに権限を付与する**。未暗号化のソースは宛先の既定暗号化になり、**ETag がソースと変わる**。SSE-C も対象 |
| EBS スナップショットのコピー | 未暗号化のスナップショットは**コピー時に暗号化できる**（KMS キーを指定。省略すると既定の KMS キー）。暗号化済みは別のキーで再暗号化してコピーできる。アカウント既定で暗号化が有効ならコピーは自動で暗号化される。別リージョン・外部へのデータ転送料金がかかる |
| RDS スナップショットのコピー（クロスリージョン） | 暗号化済みスナップショットの別リージョンへのコピーには、**宛先リージョンの KMS キーを指定**する（キーはリージョンごとのため）。共有された未暗号化スナップショットはクロスリージョンコピーできる |
| RDS クロスリージョンリードレプリカ | 09 ノート。ソースが暗号化済みで、宛先リージョンのキーを指定 |

## キーのローテーション
- **カスタマーマネージドキー**: 自動ローテーションは**既定では無効**。有効にするとキーマテリアルを**約 365 日ごと**（既定）に新規生成。**オンデマンドローテーション**もできる
- **AWS マネージドキー**は**約 365 日ごとに常に自動ローテーション**（ユーザーは設定不可）
- ローテーションは**キーマテリアルを更新するだけ**。キー ID・ARN・エイリアス・ポリシーは変わらず、**保護しているデータへの影響はない**。データの再暗号化は不要
- **自動/オンデマンドローテーションの対象は、対称暗号化キー（AWS_KMS 起点と EXTERNAL 起点）**。**非対称キー、HMAC キー、カスタムキーストアのキー**は対象外で、**新しいキーを作成してエイリアスを付け替える**「手動ローテーション」で行う
- ローテーションは**保護データのデータキーの再暗号化・ローテーションをしない**。データキーが漏えいした場合の対策にはならない

## 判断ポイント
- 「複数リージョンでキーマテリアル共通、再暗号化なし・リージョン間 KMS 呼び出しなしで復号」→ マルチリージョンキー（クライアント側暗号化、DynamoDB グローバルテーブルなど）
- 「既存のシングルリージョンキーをマルチリージョンにしたい」→ 変換不可。新しいキーで再暗号化
- 「別アカウントに KMS キーを使わせる」→ **キーポリシー + 外部アカウントの IAM ポリシーの両方**
- 「IAM ポリシーでキーを許可したのに AccessDenied」→ キーポリシーに `root` 委任文がない、または他アカウントのキーで外部側/キー側の片方が欠けている
- 「S3 CRR で SSE-KMS のオブジェクトも複製」→ SseKmsEncryptedObjects を有効化 + 宛先リージョンの KMS キーを指定 + ロールの権限
- 「暗号化 EBS/RDS スナップショットを別リージョンへ」→ 宛先リージョンの KMS キーで再暗号化してコピー
- 「未暗号化 EBS スナップショットを暗号化したい」→ コピー時に暗号化を指定
- 「ローテーションしても既存データの再暗号化は要るか」→ 不要

## Q&A（答えを隠して考えてから確認）
### Q1. 複数リージョンでキーマテリアルを共通にし、再暗号化やリージョン間の KMS 呼び出しなしで復号したい。どうする？
<details><summary>答え</summary>
マルチリージョンキー。関連キーは同じキー ID とキーマテリアルを持つ。クライアント側暗号化で最も効く。
</details>

### Q2. 既存のシングルリージョンキーをマルチリージョンキーにしたい。どうする？
<details><summary>答え</summary>
変換はできない。新しいマルチリージョンキーを作り、既存データを再暗号化する。
</details>

### Q3. 別アカウントのユーザーに自アカウントの KMS キーを使わせたい。何が必要？
<details><summary>答え</summary>
2 つの許可が両方必要。キー所有アカウントのキーポリシーで外部アカウントを許可することと、外部アカウントの IAM ポリシーで自アカウントのユーザー/ロールに委任すること。片方では不十分。
</details>

### Q4. IAM ポリシーでキーへのアクセスを許可したのに AccessDenied になる。原因の候補は？
<details><summary>答え</summary>
キーポリシーに `arn:aws:iam::<アカウント>:root` の委任文がない。KMS のキーポリシーは他のリソースポリシーと違い、アカウントに自動でアクセスを与えないため。
</details>

### Q5. S3 CRR で SSE-KMS のオブジェクトも複製したい。どうする？
<details><summary>答え</summary>
`SourceSelectionCriteria` で SseKmsEncryptedObjects を Enabled にし、宛先の対称 KMS カスタマーマネージドキー ID を指定する。レプリケーション用 IAM ロールにソースキーの `kms:Decrypt` と宛先キーの `kms:Encrypt` が必要。SSE-KMS は既定では複製されない。
</details>

### Q6. KMS キーを自動ローテーションした。既存データの再暗号化は必要？非対称キーはどうローテーションする？
<details><summary>答え</summary>
再暗号化は不要。キーマテリアルが更新されるだけで、キー ID・ARN・エイリアスは変わらない。非対称キー、HMAC キー、カスタムキーストアのキーは自動ローテーションの対象外で、新しいキーを作ってエイリアスを付け替える手動ローテーションで行う。
</details>
