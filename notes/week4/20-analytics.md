# Week4-20: 分析（Athena / Glue / Lake Formation / Redshift / Kinesis）

出典（2026-09-26 に docs.aws.amazon.com を curl で取得して原文を確認）: Kinesis Data Streams デベロッパーガイド（クォータ、モード、拡張ファンアウト、保持期間）、Amazon Data Firehose デベロッパーガイド（データ配信、ソース選択）、Athena ユーザーガイド（ワークグループのコスト管理、パフォーマンスチューニング、パーティションプロジェクション、フェデレーテッドクエリ）、Glue ユーザーガイド（クローラー、ジョブブックマーク）、Lake Formation デベロッパーガイド（クロスアカウント、タグベースアクセス制御）、Redshift（データ共有、Spectrum、Multi-AZ、スナップショットのリージョン間コピー、同時実行スケーリング）

## 選定の早見表
| 要件 | 選択 |
|---|---|
| S3 上のデータをそのまま SQL で分析（サーバーレス、スキャン量課金） | **Athena** |
| スキーマ自動検出（データカタログ）、ETL | **Glue（クローラー、Data Catalog、ETL ジョブ）** |
| データレイクの細かい権限（列 / 行 / タグ）、クロスアカウント共有 | **Lake Formation** |
| 大規模な DWH、複雑な結合、高い同時実行 | **Redshift** |
| S3 のデータも Redshift のテーブルと結合して問い合わせ | **Redshift Spectrum** |
| リアルタイムのストリームを複数のコンシューマーで処理 | **Kinesis Data Streams** |
| ストリームを S3 / Redshift / OpenSearch などへ自動配信（管理不要） | **Amazon Data Firehose** |
| ストリームをリアルタイムに集計・加工 | **Managed Service for Apache Flink** |

## Athena
- **S3 上のデータを標準 SQL で分析**する。Glue Data Catalog のテーブル定義を使う
- **ワークグループ**でクエリの実行を分離。**クエリごと・ワークグループごとのデータ使用量の制限**を設定でき、**クエリごとの上限を超えると Athena がクエリをキャンセル**し、**ワークグループの上限を超えると SNS でアラーム**を送れる。**コスト配分タグ**をワークグループに付けて Cost and Usage Report で追跡できる
- **パフォーマンス最適化**（公式ガイドの見出し）: **列指向フォーマット**、**パーティション分割とバケット化**、**パーティションプロジェクション**、S3 のスロットリング対策
- **パーティションプロジェクション**: テーブルのプロパティから Athena が**パーティションの値と場所を計算**する。Glue Data Catalog へのメタデータ問い合わせ（リモート操作）の代わりに**メモリ内で計算**するので、**パーティション数が非常に多いテーブル**のクエリが速くなり、**パーティション管理も自動化**できる
- **フェデレーテッドクエリ**: **データソースコネクタ**で他のデータソースにも SQL を実行する。接続情報は **Glue の接続**に保存し、Glue Data Catalog に登録できる。**クロスアカウントのフェデレーテッドクエリ**も設定できる（詳細は未確認）
- 判断: 「S3 のログを、サーバーレスで、たまにアドホックに SQL 分析」→ **Athena**、「スキャン量とコストを抑えたい」→ **Parquet などの列指向 + パーティション**、「チーム別にコスト上限」→ **ワークグループのデータ使用量制限**

## Glue
- **クローラー**: データストアをクロールして **Glue Data Catalog にデータベースとテーブルを作成・更新**する。**多くの Glue ユーザーが使う主な方法**（原文）。**1 回の実行で複数のデータストア**をクロールできる
- **ジョブブックマーク**: 前回のジョブ実行で**処理済みのデータの状態を保持**し、**再実行時に古いデータの再処理を防ぐ**。スケジュール実行で**新しいデータだけを処理**できる。**JDBC ソース、Relationalize 変換、一部の S3 ソースで実装**されている
- 判断: 「S3 に日次で追加されるデータだけを ETL したい」→ **ジョブブックマーク**、「S3 のデータのスキーマを自動検出して Athena で検索」→ **クローラー + Data Catalog**

## Lake Formation
- **データレイクの権限管理**を Glue Data Catalog のリソース（データベース、テーブル、列）に対して行う
- **クロスアカウント共有**: **AWS RAM** でリソースを共有する。**付与先が同じ組織のアカウントなら共有されたリソースはすぐに使える**。**別組織なら RAM の招待を受け入れる**（付与先のデータレイク管理者）
- **共有方式は 2 つ**: **名前付きリソース方式**（データベース / テーブルを直接指定）と **LF-TBAC（タグベースアクセス制御）**。**LF-TBAC は RAM を使ってクロスアカウントに付与**する
- **LF-TBAC**: **属性（LF-Tag）**をリソースに付け、プリンシパルに**タグの値**への権限を付与する。**プリンシパルの付与済みタグ値とリソースのタグ値が一致すれば許可**される。**リソースが急速に増える環境**に向く（原文）
- **リソースリンク**: **Athena や Redshift Spectrum が共有リソースをクエリに含めるには、リソースリンクが必要**
- **ハイブリッドアクセスモード**でのクロスアカウント共有もサポートされる（詳細は未確認）
- 判断: 「複数アカウントのデータレイクを、部署や機密度ごとのタグで権限管理」→ **Lake Formation の LF-TBAC + RAM**、「共有されたテーブルを Athena でクエリ」→ **リソースリンクを作成**

## Redshift
- **データ共有（datashare）**: **クラスター、ワークグループ、AWS アカウント、リージョンをまたいで、コピーや移動なしに最新（ライブ）のデータを共有**する。SELECT / INSERT / UPDATE などの権限をテーブル単位で、USAGE / CREATE をスキーマ単位で付与できる。コミット済みのデータはすぐ全ウェアハウスから見える。用途: 部門間のコラボレーション、データのサービス提供、開発・テスト・本番間の共有
- **Redshift Spectrum**: **S3 のデータをテーブルにロードせずに問い合わせる**。**処理の多くは Spectrum 層で行われ、データは S3 に残る**。**複数のクラスターが同じ S3 データを同時に問い合わせ**できる
- **Multi-AZ 配置**（RG / RA3 のプロビジョンドクラスター）: **2 つの AZ にコンピュートを配置**し**単一のエンドポイント**でアクセス。**AZ 障害時は残りの AZ のコンピュートが処理を継続**。**RPO はゼロ**。**課金は Single-AZ と同じ時間単価**で、**ストレージは共有**なので同額
- **スナップショットのリージョン間コピー**: **一度に 1 つの宛先リージョンにのみ**コピーできる。**宛先リージョンでの自動スナップショットの保持期間は、ソースリージョンとは別に設定**できる。**KMS で暗号化したクラスターは、宛先リージョンのカスタマー管理キーを Redshift が使えるよう「スナップショットコピーグラント」を作成**して指定する（ノート 10 の KMS と同じ発想）
- **同時実行スケーリング（Concurrency Scaling）**: **クラスターの容量を自動で追加**し、**読み取りと書き込みの両方のクエリ**の増加に対応。どのクエリを送るかは **WLM キュー**で設定。**Redshift Serverless** は容量を自動でプロビジョニングしてスケールし、**使った分だけ**課金（ワークグループと名前空間で管理）
- 判断: 「別アカウント / 別リージョンの Redshift に、コピーなしで最新データを共有」→ **データ共有**、「S3 のデータレイクと DWH を 1 つの SQL で結合」→ **Spectrum**、「AZ 障害に耐えたい DWH」→ **Multi-AZ（RA3）**、「DR 用にリージョン間でバックアップ」→ **スナップショットのリージョン間コピー（KMS はグラント）**、「BI の同時アクセスが急増」→ **同時実行スケーリング**

## Kinesis Data Streams（KDS）
- **容量モード**: **オンデマンド（Standard / Advantage）**と**プロビジョニング**。**オンデマンド**は容量計画不要で自動スケールし、**過去 30 日のピーク書き込みスループットの最大 2 倍**まで受け入れる。**Advantage** はアカウント単位のモードで、書き込み容量の**事前のウォーミング**、ストリームごとの固定料金なし。**プロビジョニング**は**シャード数を自分で指定**（増減可能）
- **モード切り替え**: ストリームごとに、オンデマンドとプロビジョニングを **24 時間に 2 回**まで切り替えできる。アプリは無停止で読み書きを続けられ、切り替え中のステータスは **Updating**（**Active** になるまで再変更不可）。切り替え直後のシャード数は**切り替え前を引き継ぐ**（プロビジョニング→オンデマンドは以後 Kinesis が自動調整、オンデマンド→プロビジョニングは以後シャード数を自分で管理）。**Advantage は有効化後 24 時間以上経たないと無効化できず**、アカウントで**最低 25 MiB/秒の取り込みと 25 MiB/秒の取得**を約束する（下回っても不足分を同じ割引単価で課金）。Advantage から Standard に戻すには、先に**ウォームスループット設定を削除**する
- **シャードの上限**: 1 シャードあたり**書き込み 1 MB/秒 または 1,000 レコード/秒**、**読み取り 2 MB/秒 または 2,000 レコード/秒**
- **保持期間**: **既定 24 時間、最大 8,760 時間（365 日）**
- **コンシューマー**: **共有スループット（GetRecords）**は**シャードあたり合計 2 MB/秒を全コンシューマーで共有**（遅延は 1 つで約 200 ms、5 つで約 1,000 ms）。**拡張ファンアウト（EFO）**は**コンシューマーごとに専用の 2 MB/秒/シャード**、**プッシュ型（HTTP/2 の SubscribeToShard）**で**遅延は約 70 ms**。**EFO は追加料金**（データ取得料金 + コンシューマー・シャード時間）。**登録できる EFO コンシューマーは 20（Standard / プロビジョニング）、50（Advantage）**
- 判断: 「複数のアプリが同じストリームを低遅延で読む、読み取りが競合する」→ **拡張ファンアウト**、「トラフィックが予測不能」→ **オンデマンド**、「トラフィックが安定していてコストを抑えたい」→ **プロビジョニング**（原文でも、オンデマンドは予測不能・変動の大きいワークロード向け、プロビジョニングは予測可能なトラフィック向け。具体的な単価は Developer Guide に無く未確認）、「数日〜1 年分のイベントを再処理」→ **保持期間を延長（最大 365 日）**

## Amazon Data Firehose
- **ソース**: **Direct PUT**（SDK、Lambda、CloudWatch Logs、Kinesis Agent など）、**Kinesis Data Streams**、**Amazon MSK**
- **配信先**: **S3、Redshift、OpenSearch Service / Serverless、Splunk、HTTP エンドポイント、Snowflake**
- **S3 へは、バッファリング設定に従ってレコードを連結して 1 つのオブジェクトとして配信**する。**Redshift へは、まず S3 に配信してから COPY コマンド**でロード
- **配信は少なくとも 1 回（at-least-once）**で、**重複が起こりうる**。**S3、Apache Iceberg、Snowflake の配信先は重複の対象外**（原文）
- 判断: 「ストリームを S3 / Redshift に自動でロード、運用不要」→ **Firehose**、「複数のコンシューマーで独自に処理、リプレイ」→ **KDS**、「KDS の結果を S3 にも保存」→ **KDS をソースにした Firehose**

## 判断ポイント
- 「S3 のデータをサーバーレスで SQL 分析、スキャン量を減らす」→ **Athena + Parquet + パーティション（多い場合はパーティションプロジェクション）**
- 「Athena のチーム別コスト上限」→ **ワークグループのデータ使用量制限**
- 「日次の ETL で新しいデータだけ処理」→ **Glue ジョブブックマーク**
- 「複数アカウントのデータレイクの権限をタグで管理」→ **Lake Formation LF-TBAC（RAM 経由）**
- 「別リージョンの Redshift にコピーなしで共有」→ **Redshift データ共有**
- 「DWH の AZ 障害耐性」→ **Redshift Multi-AZ（RA3、RPO ゼロ）**
- 「Redshift のリージョン間 DR」→ **スナップショットのリージョン間コピー（KMS 暗号化はスナップショットコピーグラント）**
- 「ストリームの複数コンシューマーの読み取り競合」→ **KDS 拡張ファンアウト**
- 「ストリームの S3 / Redshift への自動配信」→ **Firehose**

## Q&A（答えを隠して考えてから確認）
### Q1. S3 のログを Athena で分析していてコストが高い。スキャン量を減らすには？ また、チームごとにコスト上限を設けたい。
<details><summary>答え</summary>
Parquet などの列指向フォーマットにしてパーティション分割する（パーティションが非常に多い場合はパーティションプロジェクションでメタデータ問い合わせも減らせる）。チーム別の上限は、ワークグループごとにクエリごと・ワークグループごとのデータ使用量制限を設定する。クエリごとの上限を超えるとキャンセルされ、ワークグループの上限を超えると SNS でアラームを送れる。
</details>

### Q2. Glue の日次 ETL ジョブで、前回処理済みのデータを再処理せず新しいデータだけを処理したい。
<details><summary>答え</summary>
ジョブブックマークを有効にする。前回の実行の処理済み状態を保持し、再処理を防ぐ。JDBC ソース、Relationalize 変換、一部の S3 ソースで実装されている。
</details>

### Q3. 複数アカウントにまたがるデータレイクの権限を、部署や機密度ごとのタグで管理し、共有された表を Athena でクエリしたい。
<details><summary>答え</summary>
Lake Formation のタグベースアクセス制御（LF-TBAC）で LF-Tag をリソースに付け、タグの値への権限をプリンシパルに付与する。クロスアカウントは AWS RAM で共有される（同じ組織なら共有はすぐ使える、別組織なら招待の承認が必要）。Athena や Redshift Spectrum で共有リソースをクエリするにはリソースリンクが必要。
</details>

### Q4. 別アカウント / 別リージョンの Redshift クラスターに、データをコピーせず最新のデータを共有したい。
<details><summary>答え</summary>
Redshift のデータ共有（datashare）。クラスター、ワークグループ、アカウント、リージョンをまたいでライブのデータを共有できる。コピーや移動は不要で、コミット済みのデータはすぐ見える。
</details>

### Q5. Redshift を AZ 障害に耐えられるようにし、さらにリージョン障害に備えたバックアップも持ちたい。KMS で暗号化している。
<details><summary>答え</summary>
AZ 障害には Multi-AZ 配置（RG / RA3 のプロビジョンドクラスター、2 つの AZ に配置し単一エンドポイント、RPO ゼロ、時間単価は Single-AZ と同じ）。リージョン障害には、スナップショットを別リージョンにコピーする（宛先は一度に 1 リージョン）。KMS 暗号化のクラスターは、宛先リージョンのカスタマー管理キーを Redshift が使えるようスナップショットコピーグラントを作成して指定する。
</details>

### Q6. 同じ Kinesis データストリームを複数のアプリが読み、読み取りが競合して遅延が増えている。どうする？ ストリームのイベントを 1 か月分保持して再処理もしたい。
<details><summary>答え</summary>
拡張ファンアウト（EFO）を使う。コンシューマーごとに専用の 2 MB/秒/シャードを持ち、プッシュ型で遅延は約 70 ms。共有スループットはシャードあたり合計 2 MB/秒を全コンシューマーで共有し、5 つで約 1,000 ms まで遅延が増える。EFO は追加料金あり、登録上限は 20（Advantage は 50）。保持期間は既定 24 時間から最大 365 日まで延長できる。
</details>
