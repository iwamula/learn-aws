Week1-7: セキュリティサービスの組織横断集約

共通の型

  1. 管理アカウントで Organizations との信頼されたアクセスを有効化
  2. 委任管理者（通常はセキュリティ/監査アカウント）を指定し、管理アカウントでの日常運用を避ける
  3. 新規メンバーアカウントへの自動有効化を設定
  4. 委任管理者に検出結果・構成データを集約

セキュリティ系サービスは、可能なら同じアカウントを委任管理者に統一すると1か所で確認できる（Security Hub の推奨）。

サービス別

サービス 集約の仕組み 押さえどころ
CloudTrail 組織の証跡（管理アカウント、または委任管理者が作成）が全メンバーのイベントを記録。メンバーアカウントにも同名の証跡コピーが作られる 組織証跡の所有者は常に管理アカウント。コンソール作成は既定でマルチリージョン
GuardDuty 委任管理者 + メンバー。自動有効化は NEW（新規のみ）/ ALL（既存含む全アカウント）/ NONE リージョンサービス。委任管理者の指定とメンバー追加をリージョンごとに行う。ALL/NEW → NONE にしても既存アカウントは無効化されない
Security Hub (CSPM) 委任管理者。中央設定 (central configuration) で組織/OU/アカウントに設定ポリシー（有効化するスタンダード・コントロール）を適用 管理アカウントは委任管理者にできない。ホームリージョン（+リンクリージョン）を指定しないと中央設定を使えず、リージョンごとの個別設定になる。中央管理のアカウントは管理者だけが変更可（ドリフト防止）
AWS Config アグリゲーターで複数アカウント/リージョンのデータを1アカウント・1リージョンに集約。組織を指定すれば個別の承認不要（サービスリンクロール） 委任管理者でも組織全体を集約可能。メンバーで Config が有効なことが前提。Config ルールは API で組織全体のアカウントに展開できる
Macie 管理アカウントが委任管理者を指定（信頼されたアクセスが必要。コンソールで指定すれば自動で有効化） リージョンサービスで、委任管理者の指定もリージョンごと。1 つの管理者アカウントで最大 5,000 アカウントを管理（AWS ブログ）
Inspector 管理アカウントが委任管理者を指定。委任管理者はメンバーのスキャン有効化・組織全体の検出結果の集約・抑制ルールの管理ができる inspector2:enableDelegatedAdminAccount を使うリージョンごとに呼ぶ。Organizations のポリシーで有効化を一元管理する方式もある（メンバーは API で変更不可）
Detective 管理アカウントがリージョンごとに Detective 管理者を指定すると、Organizations の委任管理者にもなる 管理アカウント自身を Detective 管理者にもできる（その場合は委任管理者にならない）。Organizations に委任管理者がいれば、その委任管理者か管理アカウントのどちらかしか選べない
Firewall Manager 管理アカウントがデフォルト管理者を 1 つ指定すると、自動で Organizations の委任管理者になる 追加で最大 9 つの管理者（管理範囲を OU / リージョン / ポリシー種別で制限）を作れる。デフォルト管理者の変更は既存管理者が先に自分を revoke する必要がある（ポリシーも削除される）

判断ポイント

  • 「全アカウント・全リージョンの API ログを1か所に、改ざんを防ぎたい」→ 組織証跡 + Log Archive アカウントの S3 + ログファイルの整合性検証（改ざん・削除の検知）。改ざん・削除の防止は S3 Object Lock（AWS SRA Log Archive の記述）、ダイジェストファイルの保護強化には S3 MFA Delete（CloudTrail 整合性検証ドキュメント）
  • 「新規アカウントでも GuardDuty を自動で有効に」→ 委任管理者で自動有効化（NEW か ALL）
  • 「Security Hub の標準/コントロールを全アカウントで統一し、勝手に変更させない」→ 中央設定ポリシー
  • 「全アカウントのリソース構成とコンプライアンスを1画面で」→ Config 組織アグリゲーター
  • 「ルールに反するリソースを組織全体で検出」→ Config ルールの組織展開（API）、または Control Tower の発見コントロール
  • 「管理アカウントを使わずにセキュリティ運用」→ 委任管理者（管理アカウントには最小限の人だけ）
  • 「複数リージョンの GuardDuty を見たい」→ リージョンごとに設定が必要（Security Hub のリージョン集約と組み合わせる）

Q&A（答えを隠して考えてから確認）

Q1. 新規に作成されるメンバーアカウントでも GuardDuty を自動で有効にしたい。どうする？

答え 委任管理者で自動有効化を設定する（`NEW` は新規のみ、`ALL` は既存含む全アカウント）。GuardDuty はリージョンサービスなので、委任管理者の指定とメンバー追加をリージョンごとに行う。

Q2. GuardDuty の自動有効化を NONE に変更した。既存アカウントの GuardDuty は無効になる？

答え 無効化されない。`ALL/NEW` から `NONE` にしても既存アカウントは無効化されない。

Q3. Security Hub の標準/コントロールを全アカウントで統一し、メンバーに勝手に変更させたくない。どうする？

答え 委任管理者で中央設定（central configuration）の設定ポリシーを組織/OU/アカウントに適用する。中央管理のアカウントは管理者だけが変更可でドリフトを防げる。ホームリージョンの指定が必要で、管理アカウントは委任管理者にできない。

Q4. 全アカウント・全リージョンのリソース構成とコンプライアンスを1画面で見たい。どうする？

答え Config の組織アグリゲーター。組織を指定すれば個別の承認は不要（サービスリンクロール）で、委任管理者でも組織全体を集約できる。メンバーで Config が有効なことが前提。

Q5. 全アカウントの API ログを1か所に集約したい。組織証跡の所有者は誰？

答え 組織の証跡を作成する。管理アカウントまたは委任管理者が作成できるが、組織証跡の所有者は常に管理アカウント。メンバーアカウントにも同名の証跡コピーが作られる。

Q6. 組織横断のセキュリティサービスを設定する共通の手順は？

答え 1. 管理アカウントで Organizations との信頼されたアクセスを有効化。2. 委任管理者（通常はセキュリティ/監査アカウント）を指定。3. 新規メンバーアカウントへの自動有効化を設定。4. 委任管理者に検出結果・構成データを集約。可能なら同じアカウントを委任管理者に統一する。
