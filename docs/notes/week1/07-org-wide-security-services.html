Week1-7: セキュリティサービスの組織横断集約

共通の型

  1. 管理アカウントで Organizations との信頼されたアクセスを有効化
  2. 委任管理者（通常はセキュリティ/監査アカウント）を指定し、管理アカウントでの日常運用を避ける
  3. 新規メンバーアカウントへの自動有効化を設定
  4. 委任管理者に検出結果・構成データを集約

セキュリティ系サービスは、可能なら同じアカウントを委任管理者に統一すると1か所で確認できる（Security Hub の推奨）。

サービス別

サービス 集約の仕組み 押さえどころ
CloudTrail 組織の証跡（管理アカウント、または委任管理者が作成）が全メンバーのイベントを記録。メンバーアカウントにも同名の証跡コピーが作られる 組織証跡の所有者は常に管理アカウント。コンソール作成は既定でマルチリージョン
GuardDuty 委任管理者 + メンバー。自動有効化は NEW（新規のみ）/ ALL（既存含む全アカウント）/ NONE リージョンサービス。委任管理者の指定とメンバー追加をリージョンごとに行う。ALL/NEW → NONE にしても既存アカウントは無効化されない
Security Hub (CSPM) 委任管理者。中央設定 (central configuration) で組織/OU/アカウントに設定ポリシー（有効化するスタンダード・コントロール）を適用 管理アカウントは委任管理者にできない。ホームリージョン（+リンクリージョン）を指定しないと中央設定を使えず、リージョンごとの個別設定になる。中央管理のアカウントは管理者だけが変更可（ドリフト防止）
AWS Config アグリゲーターで複数アカウント/リージョンのデータを1アカウント・1リージョンに集約。組織を指定すれば個別の承認不要（サービスリンクロール） 委任管理者でも組織全体を集約可能。メンバーで Config が有効なことが前提。Config ルールは API で組織全体のアカウントに展開できる
Macie / Inspector / Detective / Firewall Manager 同様に委任管理者方式 未確認（今回は原文で裏取りしていない。次回確認）

判断ポイント

  • 「全アカウント・全リージョンの API ログを1か所に、改ざんを防ぎたい」→ 組織証跡 + Log Archive アカウントの S3（改ざん防止の具体策は別途確認）
  • 「新規アカウントでも GuardDuty を自動で有効に」→ 委任管理者で自動有効化（NEW か ALL）
  • 「Security Hub の標準/コントロールを全アカウントで統一し、勝手に変更させない」→ 中央設定ポリシー
  • 「全アカウントのリソース構成とコンプライアンスを1画面で」→ Config 組織アグリゲーター
  • 「ルールに反するリソースを組織全体で検出」→ Config ルールの組織展開（API）、または Control Tower の発見コントロール
  • 「管理アカウントを使わずにセキュリティ運用」→ 委任管理者（管理アカウントには最小限の人だけ）
  • 「複数リージョンの GuardDuty を見たい」→ リージョンごとに設定が必要（Security Hub のリージョン集約と組み合わせる）
