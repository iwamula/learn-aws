# IAM

Q1 アカウントAとBがある。AにあるIAMユーザから、BにあるIAMロールを引き受けるには、どのようにすれば良いか。

A1. 
両側の許可が必要です（クロスアカウントでは片方だけでは不可）。

手順は次のとおりです。
1. B側で、IAMロールの信頼ポリシーに、Aのアカウント（またはAの特定ユーザー/ロール）を Principal に指定し、sts:AssumeRole を Allow します。例: {"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::<A>:user/alice"},"Action":"sts:AssumeRole"}
2. A側で、ユーザーに arn:aws:iam::<B>:role/<ロール名> への sts:AssumeRole を Allow するIAMポリシーを付与します。
3. ユーザーが aws sts assume-role（またはコンソールの「ロールの切り替え」）を実行し、一時認証情報（AccessKeyId / SecretAccessKey / SessionToken）を得て使います。

補足です。
一時認証情報の有効期間は既定1時間です（ロールの最大セッション時間まで設定可。ロールチェーンは最大1時間）。
権限は「ロールの権限ポリシー」になり、元のユーザーの権限は使えなくなります。
SCP、permissions boundary、セッションポリシーで絞られます。
第三者アカウントに許可する場合は sts:ExternalId 条件で confused deputy を防ぎます。

Q2 Q1のように、別アカウントのIAMロールを引き受ける場面としては具体的にどのようなケースがあるか。

代表的なケースは次のとおりです。

- マルチアカウント運用: 踏み台/管理アカウントから本番・開発など各アカウントへ切り替えてアクセスします（Organizations の OrganizationAccountAccessRole など）。
- ログ・監査の集約: セキュリティアカウントが各アカウントのロールを引き受けて調査します。または各アカウントが中央のログアカウントの S3 へ書き込みます。
- SaaS/サードパーティ連携: 外部ベンダーが自社アカウントのロールを引き受けて監視やコスト分析を行います（ExternalId は事実上必須）。
- CI/CD: ツール用アカウントのパイプラインが、デプロイ先アカウントのロールを引き受けます（CodePipeline のクロスアカウントデプロイ）。
- リソースベースポリシーを持てないサービスへのアクセス: S3 や SQS などはバケット/キューポリシーで他アカウントに直接許可できます。一方、リソースポリシーを持たないサービス（EC2 の API 操作など）は、AssumeRole で相手アカウントのロールになるしかありません。また AssumeRole すると元アカウントの権限は使えなくなるため、リソースポリシー方式なら「自アカウントの権限を保ったまま」他アカウントのリソースを扱えます。ここが使い分けの判断材料です。

AWS IAM Identity Center も内部的には各アカウントのロールへ一時認証情報を払い出しています。
試験では「長期アクセスキーを共有せず、最小権限で、監査可能に」という文脈で AssumeRole が正解になることが多いです。

Q3. Q2のExternalIdとはなんですか？どのように設定しますか？

ExternalId は、ロールを引き受ける側（主にサードパーティ）が AssumeRole のときに一緒に送る文字列で、ロールの信頼ポリシーがその値の一致を要求する仕組みです。主な目的は confused deputy 問題（権限を持つ第三者が、別の顧客に頼まれて自分の権限を悪用させられること）の防止です。

典型例です。SaaS ベンダーの Example Corp が、顧客 A と顧客 B のアカウントのロールを引き受けて監視する場面を考えます。ExternalId がないと、悪意ある顧客 B が「顧客 A のロールARN」を Example Corp に登録するだけで、Example Corp に顧客 A のロールを引き受けさせてしまう恐れがあります。そこで Example Corp が顧客ごとに固有の ExternalId を発行し、各顧客はそれをロールの信頼ポリシーに条件として書きます。Example Corp は AssumeRole のたびに、その顧客の ExternalId を必ず付けます。

設定は2か所です。
1つ目は、ロールを持つ側（顧客側）の信頼ポリシーです。Condition に sts:ExternalId を入れます。例: "Condition": {"StringEquals": {"sts:ExternalId": "Example Corpが発行した一意のID"}}
2つ目は、引き受ける側です。AWS CLI なら aws sts assume-role に --external-id を付けます。API なら AssumeRole の ExternalId パラメータに指定します。

注意点は次のとおりです。
ExternalId は秘密情報ではありません。パスワードやアクセスキーのような秘匿値ではなく、あくまで「どの顧客のための操作か」を区別する識別子です。公式ドキュメントにも、AWS は ExternalId を秘密として扱わないと書かれています。
値は、顧客ではなくサードパーティ側が生成します。顧客に決めさせると、顧客間で値が重複したり、他の顧客の値を指定されたりして意味を失うためです。マルチテナントなら顧客（AWSアカウント）ごとに1つ、推測されにくいランダム文字列にします。
値は2〜1,224文字で、英数字（空白なし）と + = , . @ : / - が使えます。
コンソールの「ロールの切り替え」では、ExternalId が必要なロールには切り替えられません。CLI か API の AssumeRole を使う必要があります。
自社内の別アカウント同士（自分で両方管理している場合）では、通常は ExternalId は不要です。ExternalId が効くのは、自分以外の第三者にロールを引き受けさせる場面です。

試験での判断: 「サードパーティに自アカウントへのアクセスを許可する。confused deputy を防ぎたい」なら、クロスアカウントロール + sts:ExternalId 条件です。アクセスキーの共有は不正解になります。
根拠: IAM User Guide「External IDs for third party access」原文。
