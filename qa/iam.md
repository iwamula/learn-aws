# IAM

Q1 アカウントAとBがある。AにあるIAMユーザから、BにあるIAMロールを引き受けるには、どのようにすれば良いか。

> **AI回答（2026-09-25）**
> 両側の許可が必要（クロスアカウントでは片方だけでは不可）。
> 1. **B側**: IAMロールの**信頼ポリシー**で、Aのアカウント（またはAの特定ユーザー/ロール）を Principal に指定し、`sts:AssumeRole` を Allow する。
>    ```json
>    {"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::<A>:user/alice"},"Action":"sts:AssumeRole"}
>    ```
> 2. **A側**: ユーザーに、`arn:aws:iam::<B>:role/<ロール名>` への `sts:AssumeRole` を Allow する**IAMポリシー**を付与する。
> 3. ユーザーが `aws sts assume-role`（または コンソールの「ロールの切り替え」）を実行し、一時認証情報（AccessKeyId / SecretAccessKey / SessionToken）を得て使う。
>
> 補足:
> - Principal を**アカウントID（`...:root`）**にしても**特定ユーザーARN**にしても、クロスアカウントでは**A側のIAMポリシーも必要**（同一アカウント内なら信頼ポリシーだけで足りる場合がある点との違い）。`...:root` の場合は「Aの管理者が誰に委任するか」をA側IAMポリシーで決める。
> - 一時認証情報の有効期間は既定1時間（ロールの最大セッション時間まで設定可。ロールチェーンは最大1時間）。
> - 権限は「ロールの権限ポリシー」になる（元のユーザーの権限は使えなくなる）。
> - SCP / permissions boundary / セッションポリシーで絞られる。
> - 第三者アカウントに許可する場合は `sts:ExternalId` 条件で confused deputy を防ぐ。

Q2 Q1のように、別アカウントのIAMロールを引き受ける場面としては具体的にどのようなケースがあるか。

> **AI回答（2026-09-25）**
> - **マルチアカウント運用**: 踏み台/管理アカウントから本番・開発など各アカウントへ切り替えてアクセス（Organizations の `OrganizationAccountAccessRole` など）。
> - **ログ・監査の集約**: セキュリティアカウントが各アカウントのロールを引き受けて調査、または各アカウントが中央のログアカウントの S3 へ書き込む。
> - **SaaS/サードパーティ連携**: 外部ベンダーが自社アカウントのロールを引き受けて監視やコスト分析を行う（ExternalId 必須級）。
> - **CI/CD**: ツール用アカウントのパイプラインが、デプロイ先アカウントのロールを引き受ける（CodePipeline のクロスアカウントデプロイ）。
> - **リソースベースポリシーを持てないサービスへのアクセス**: S3 や SQS などはバケット/キューポリシーで他アカウントに直接許可できるが、リソースポリシーを持たないサービス（EC2 の API 操作など）は、AssumeRole で相手アカウントのロールになるしかない。また AssumeRole すると元アカウントの権限は使えなくなるため、リソースポリシー方式なら「自アカウントの権限を保ったまま」他アカウントのリソースを扱える点が使い分けの判断材料。
> - **AWS IAM Identity Center** も内部的には各アカウントのロールへ一時認証情報を払い出している。
>
> 試験では「長期アクセスキーを共有せず、最小権限で、監査可能に」の文脈で AssumeRole が正解になることが多い。
